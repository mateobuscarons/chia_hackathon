# CHIA Hackathon: an LLM agent with a memory that survives a workload class it never saw

A3 workshop hackathon (agentic-arch.org). Deliverable: 4-page paper + open-sourced CHIA loop with reproducible results; "reusable CHIA blocks upstreamed to mainline" is an explicit track. Judged by the A3 program committee, run by the six organizers: Gonzalez and Jain (Google, ArchAgent authors), Karandikar (UC Berkeley, CHIA PI), Yazdanbakhsh (Google DeepMind, ArchGym: "all optimizers tie under tuned hyperparameters"), Huang (NVIDIA, DOSA), Skarlatos (CMU). They reward novelty and quality of the agentic architecture, matched-budget baselines, seeds, realizability, and reusable blocks + datasets. Not raw IPC.

**The judges' own paper, and the open problem we answer.** ArchAgent (Gupta, Jain, Gonzalez et al., arXiv 2602.22425; four of the six organizers are authors) has an agent write cache-replacement policies inside ChampSim: +5.3% IPC on multi-core Google traces, +0.9% on SPEC06, cascaded evaluation, workloads admitted by LLC MPKI > 1. Its authors state three things it does not do: it starts every search from scratch (no transfer), its hypotheses stay unscored free text, and "overfitting versus specialization, extrapolation from representative workloads" is an open community problem. We answer the third with the first two as supporting claims. Their margins are 1-3% and come from new policies; we search a knob space; we never compare on IPC.

## The mechanism

**One sentence:** an LLM agent tunes the cache hierarchy from the results table and the workloads' trace-profiled descriptors, and carries a memory written entirely by the system from earlier searches; the memory has two shelves so that facts (measured, gated by descriptor similarity) and strategies (procedural, from wins and failures) can be ablated separately.

- **The agent** (`loop/memory.py`, `run_agent`): each round it proposes 2 untested in-budget designs with a point forecast and a confidence; a proposal outside the space, over the area budget or already measured is rejected; the LLM gets one retry with the rejected designs listed, and if the slot is still empty it goes to a deterministic one-knob perturbation of the incumbent (never a random design; both are logged). Its forecast is a bet (P = (1 + confidence) / 2 that the measured value lands within 5%), Brier-scored. Gemini 2.5 Pro, temperature 0.7. `llm_direct` is this agent with no shelf open; `memory` opens both shelves (the single-shelf ablation arms ran in w1 and are retired). One code path, so with an empty memory the two arms are the same agent (checked).
- **The prompt**, assembled from data in this order: problem (chip parameters, area budget, knobs); workloads (every descriptor per workload, plus each workload's share of the suite gain so far); distance to memory (nearest case per workload and its percentile among pairwise case distances); nearest cases (k = 3 per workload); facts within the median past similarity and their own gate (cap 10, ranked by pairs / (1 + distance)), or the line "Facts retrieved: 0 of N"; strategies (failures first, then runs supporting and record, cap 12); the agent's own forecasting record in this search; the results table (per workload: IPC, L2 MPKI, LLC MPKI, LLC hit ratio; each row tagged start / opening move / own pick / perturbation); the task. The prompt never says what to trust; it prints numbers. Every round's full prompt is stored in the report (`rounds[].prompt`).
- **Memory shelves** (`memory.json`, nothing seeded, nothing deleted): *cases*, one per (chip, workload): descriptors, start and best design, best metric, the five largest single-knob effects with >= 3 controlled pairs; *facts*, one per measured knob step per workload: effect, pairs, bucket (small < 3%, medium 3-10%, large > 10%), descriptors of where, record (cited / improved / worsened / direction_wrong_at) and a similarity gate that tightens where the direction failed; *strategies*: procedure / failure / structure notes written by one reflection call after each run (or from the cases when no search exists), qualitative: knob and descriptor names only, a linter rejects any chip, workload or family name and any number; *forecast_log*. Facts and cases are per workload, never per suite. Descriptors are read against the UNTOUCHED chip, never the start design (a case and a current workload must share one definition).
- **Opening move** (memory arms, round 1, one mechanical slot; the other slot goes to the LLM): the START with the decisive knob flipped, the knob of largest mean absolute measured effect across the retrieved cases, set to the strongest alternative value those cases measured. Tested on the start's own geometry: the first w1 run opened with a remembered design in its own 2 MB-LLC geometry and its va_ampm_lite variant lost there, which cost two designs and taught the wrong lesson. (Max disagreement of best values was rejected: inert knobs wander, so they disagree most.) **No random fills:** a duplicate or invalid proposal gets one retry with the rejected designs listed, then a deterministic one-knob perturbation of the incumbent (the first w1 run lost 13-17% of two arms' budgets to random designs).
- **Scoreboard:** a cited fact or strategy is scored once per run by the mean percentile of the picks citing it against the picks that did not (the run's median when everything cites; "below the incumbent" punished every probe); facts also settle by controlled pair on the current workloads (wrong bucket -> re-bucket; wrong direction -> gate tightened to that distance); strategies with worsened > improved after 4 citations are demoted below the rest but kept. Consolidation (`consolidate`): union of cases, facts and forecasts; strategies grouped by the LLM (ids only), records summed and evidence unioned by the code, linted.
- **Baselines** (`loop/loop.py`, GP arms): `bo` (cold GP + expected improvement over a seeded 20k-design feasible sample), `bo_pooled` (the same warm-started with every training-chip row), `rules` (GP + rules distilled from result tables as bounded mean shifts, claim tests and stall scans; kept for cell w1's later ablation, not run while iterating), `random`. Rule claims anchor on the untouched chip; controlled pairs are found from any two measured designs one knob apart.
- **Guardrails:** rebuild per config, budget check on every proposal, CHIA smoke of every arm before any launch, every launch through `run_chia.py` with the profiler on.

Expanded on Sep 10 from 207k designs because six seeds of pilots showed only three decisive moves (L2 prefetcher, LLC size, LLC prefetcher off) and a plateau; real teams tune prefetchers and replacement at every level and the cross-level interactions are where the agent reasoned well and the GP did not. **Chips** (`loop/socs.py`, placeholders): A mobile, B mid-range (stock ChampSim), C server (wide core, 2 memory channels, 4608 KB budget); D (4-core) kept unused. Chips differ in provisioning, not hierarchy shape (block size fixed: the miss-ratio curve is measured in 64-byte blocks). The chip axis is non-trivial (A's best ranks 314th of 447 on C; C's best does not fit A or B).

**Pre-registered predictions** live in `PREREGISTRATION.md` (P1-P8 settled; P-W1-a/b/c, P-W2-a/b, P-K open) and are Brier-scored against the authors' stated probabilities.

**Written before w1's results, on purpose:** on the class boundary the memory behaves exactly as designed: the similarity gate retrieved 0 of 127 facts, all three GAP workloads sit beyond every pairwise distance between the SPEC cases, and the strategies carry only procedure, including two interaction statements the SPEC runs did produce (prefetcher x replacement). It knows it is far from home and brings only procedure. Not to be rewritten after the results.

2. **Think and research further agentic possibilities for the memory level** (detail below).
3. **Test it in w2, and keep trying w1.** w2 = the same-family test with a set that has headroom, memory consolidated from w1's runs (`python -m loop.memory consolidate` over `results/experiment_w1b_memory_run-*.json`). w1 again with more seeds, and with the question whether an agent that carries w1's own reflections ("an aggressive L2 prefetcher can pollute the LLC") learns to probe `llc_prefetcher = no`, the move behind 0.6419 that only 3 of 10 runs tried.

**What the w1 runs taught, to carry into the next cells (the user's reading of the results):**

- The two per-workload winners conflict: va_ampm_lite at L2 lifts bfs.urand (+15%) and leaves pr.urand flat; va_ampm_lite at L1D lifts pr.urand (+10%) and leaves bfs.urand flat; both together lose on bfs.urand (LLC hit ratio 0.55 -> 0.44: two aggressive prefetchers pollute the LLC). One design, two workloads pulling opposite ways: the industrial problem, and the reason the suite plateau sits where it does.
- The agents had the pollution evidence in the table and still never tested removing the LLC prefetcher: in the old space that knob was binary and got probed by habit; in the new space it has three other prefetchers that were probed instead of "none". The reflection then wrote the pollution strategy one cell late. This is the mechanism's test, not something to hand-fix.
- The opening move must test the decisive knob on the start's own geometry (a remembered design in its own geometry taught the wrong lesson); random fills must never happen (they cost 13-17% of two arms' budgets in the first run); a scoreboard that punishes every probe measures the run, not the strategy.
- Facts measured on SPEC are a coin on GAP (56% of 834 sign bets); strategies carry; the memory arm's edge over the plain agent was calibration (Brier 0.14 vs 0.18) and the opening move, not the facts.

**Two research directions (user, Sep 10):**

1. **Three levels of intelligence under one identical simulation budget.** (i) The statistics / heuristics level, made as strong as possible: today `bo` and `bo_pooled`; candidates are better acquisition functions and kernels, trust regions, architect heuristics such as "prefetcher first, then capacity", warm starts from every cached row, ensembles, and any tuned optimiser from the ArchGym family. (ii) The plain LLM agent (`llm_direct`). (iii) The memory / agentic level (`memory` and whatever agentic machinery comes next). The competition at level (i) must be strengthened before the paper claims anything about (ii) and (iii): a weak baseline proves nothing to this committee (Yazdanbakhsh: "all optimizers tie under tuned hyperparameters"). The invariant is the budget: same start, same designs per run, same seeds, same fidelity for all three.
2. **Agentic systems research for level (iii).** Survey and try agentic tools and techniques that could improve the memory agent or add to it: memory architectures (episodic vs procedural stores, retrieval by similarity vs by outcome, reflection and self-critique loops, skill libraries), planning over rounds (budget-aware look-ahead or tree search over designs), tool use (letting the agent query the tables, run the offline gates, or fit its own surrogate), multi-agent roles (proposer / critic / verifier), and calibration training from the forecast ledger. Each idea enters as an ablatable arm under the same budget, never as a silent change to the existing arms.

**Also open (lower priority):** collecting fotonik3d and cam4 on chip C (~900 simulations) to widen the SPEC memory to five workloads; cell k (the chip-boundary control); CACTI area/energy post-hoc; chip D; more seeds for whatever cell becomes the headline.

**Knobs and area model, spelled out.** 13 knobs: `l1d_sets` {32, 64, 128}, `l1d_ways` {8, 12}, `l1d_prefetcher` {no, next_line, ip_stride, va_ampm_lite}, `l2_sets` {256, 512, 1024, 2048}, `l2_ways` {4, 8, 16}, `l2_prefetcher` {no, spp_dev, ip_stride, next_line, va_ampm_lite}, `l2_replacement` {lru, srrip, drrip, ship}, `l2_mshr` {16, 32, 64}, `llc_sets` {1024, 2048, 4096, 8192}, `llc_ways` {8, 16}, `llc_prefetcher` {no, next_line, ip_stride, spp_dev}, `llc_replacement` {lru, srrip, drrip, ship}, `llc_mshr` {32, 64, 128}. Area proxy = data capacity of L2 (times the core count) plus LLC, in KB, at 64-byte blocks, checked against the chip's budget (A 2048, B 3072, C 4608, D 8192 KB); the L1D and the MSHRs carry no area. Latency: the fixed `latency` fields of L1D, L2C and LLC are deleted from the config, so ChampSim derives each cache's latency from its size (round((sets x ways)^0.343 x 0.416) cycles), and a bigger cache is slower. The ChampSim config is the stock `champsim_config.json` with the chip profile's overrides applied (`socs.apply_profile`), then the 13 knobs written into the L1D / L2C / LLC sections (`configs.build_config`); one binary is built per design and cached by content hash.

## Workloads

**Descriptors** (`loop/trace_profile.py`, `champsim_problem.chip_descriptors`): from the trace alone (accesses per kilo-instruction, write fraction, footprint, stride-regular fraction, local-reuse fraction) and the trace read against the chip's untouched geometry (footprint ratios, predicted LRU miss ratios from footprint theory, and **movable MPKI**: misses per kilo-instruction a bigger L2 / LLC would remove between the chip's size and the largest its budget affords). The chip's measured speed is never a descriptor.

**Admission gate** (`python -m loop.offline admit`, free): capacity channel = miss-ratio curve moves >= 1 MPKI across the buyable capacities (validated against measured chip C variance shares); policy channel = miss floor >= 5 MPKI. 25 traces screened. Training (SPEC17): mcf 12.6 movable, cam4 5.0, fotonik3d 3.9, pop2 2.7, omnetpp 2.6 (capacity); lbm (prefetcher, 0.96 of its variance). Rejected: gcc (43 MB footprint, 100% compulsory, curve flat from 16 KB to 32 MB), xalancbmk (1.3 MPKI), xz, roms, x264, deepsjeng, imagick, leela, nab, cactuBSSN, exchange2 (18 KB, never leaves L1). Most of SPEC does not touch memory hard enough to test a cache hierarchy: our own measurement of ArchAgent's claim.

Two hypotheses the data killed: the simulation window is not the lever (bfs.kron is capacity-flat at 10M, 30M, 45M: its footprint grows with the window); the graph input alone does not decide (bfs.urand is capacity-bound, pr.urand on the same graph is a sequential scan). Capacity sensitivity is screened per trace.

**GAP set 1** was chosen for diversity of binding constraint, not headroom, so the gate is a prediction instrument: doubling the LLC on chip C is +10.5% on bfs.urand and -0.7% / -1.2% on pr.urand / bfs.kron, exactly as the gate said from the traces alone; `ship` is +11.5% on bfs.urand; any L2 prefetcher is +90-186% on the two prefetcher workloads. From the untouched chip the suite headroom is +132%; from chip B's best +18%; from chip C's SPEC best (w1's start, 0.6014) the old-space best is 0.6419, about +7%; the expanded space may add more (reference sample pending).

**GAP set 2, defined** (Sep 11) = **sssp.kron-246B + cc.urand-353B + cc.twitter-15B**, from the untouched chip. Chosen by measurement, not by the gate: 11 designs (the stock chip, the four L2 prefetchers, srrip and ship at the LLC, the LLC doubled to 4 MB, the L2 doubled to 1 MB, and the two best composites GAP set 1 ever found) were simulated on each of six candidates and every 3-subset ranked by **the share of headroom no single knob reaches**. That share, not raw headroom, is what w1 lacked.

| set | stock | best of 11 | headroom | beyond one knob |
|---|---|---|---|---|
| GAP set 1 (w1's workloads, the benchmark) | 0.2629 | 0.6426 | +144.5% | **29.7%** |
| **sssp.kron + cc.urand + cc.twitter (set 2)** | 0.1656 | 0.2210 | **+33.5%** | **61.8%** |
| sssp.urand + cc.urand + cc.twitter | 0.1651 | 0.2194 | +32.9% | 62.7% |
| sssp.kron + cc.urand + tc.urand | 0.1352 | 0.1705 | +26.2% | 64.6% |

**Why this set: the workloads disagree by kernel.** Both shortest-path workloads want a replacement policy (`ship` alone is +19.8% on sssp.kron and +20.7% on sssp.urand) while both connected-components workloads want a prefetcher (`spp_dev` +18.8% on cc.urand, `ip_stride` +14.1% on cc.twitter, where `ship` is worth only 3-5%). No single move satisfies both, so the suite optimum must be searched. On GAP set 1 two of three workloads wanted the same L2 prefetcher, which is why one knob handed over 70% of the gain and the arms tied. Three graph types (kron, urand, twitter), two kernels, and `ship` being the dominant lever on half the suite puts the cell in the judges' own territory (ArchAgent is a replacement-policy paper). Per workload, headroom / share beyond one knob: sssp.kron 29.3% / 32.5%, cc.urand 41.0% / 54.2%, cc.twitter 32.7% / 56.8%. The +33.5% is a LOWER bound: 11 designs of 5.4 M were measured, and the reference sample is still owed.

**Rejected after probing:** `bc.urand-3004B` (+3.1% headroom, 0% beyond one knob, `ship` makes it worse; every miss is compulsory, so it would be bfs.kron's dead weight again) and `tc.urand-455B` (good structure, 49% non-trivial, but only +10.3% headroom). `sssp.urand-3988B` is a fine alternative, marginally better on non-trivial share and worse on headroom and on the gate's capacity channel.

**GAP set 2 as FIRST defined had no headroom** (Sep 10, superseded): from the SPEC-best start, bfs.road / pr.web / pr.road read LLC MPKI 0.11 / 0.32 / 1.41; after 22 designs the start was still the best. Predictable from the gate (all three policy-only) and abandoned mid-run.

**AI/ML inference traces: screened and rejected** (Sep 11, 11 traces from the DPC4 bucket covering llama2.c at four model sizes, stable-diffusion, vit, whisper, bark, clip, rwkv, biogpt). **Zero admit as capacity-sensitive**; eight are policy-only and three are rejected outright. Stride regularity runs 0.70-0.99 and misses are almost entirely compulsory (biogpt 140 of 145 MPKI, rwkv 111 of 111). The llama2 size ladder does not exist as an experiment: 15M, 42M, 110M and 7B parameters give the same footprint (21.4-21.8 MB) and the same miss rate (34.3-35.0) in a 10M-instruction window, because the engine streams weights sequentially and a bigger model only means getting less far. These are pr.urand with different names. Worth one line in the paper as the counterpart to "most of SPEC does not touch memory hard enough": AI inference touches it very hard but too predictably, so it exercises a prefetcher and nothing else. Screening cost 11 downloads and no simulation.

**Practical note:** a GAP kernel's Zenodo zip (record 20043527) is 10 GB with 13-31 traces of 24-690 MB; `python -m loop.collect fetch_gap <zip url> <member> traces` byte-ranges one member (bc, bfs, cc, pr, sssp, tc and two XSBench zips). The DPC4 bucket (`https://pub-c31f67d79d1b4cd28ff320612b1a9f84.r2.dev/manifest.txt`, 610 current-format traces, 1.4 TB: 359 Google datacenter `gtrace_v2`, 80 ai-ml, 79 graph, 92 SPEC17) serves plain HTTP ranges, so a 100 MB prefix (~88M instructions, 54:1 compression) is enough to profile and screen a trace without downloading it; ChampSim reads `.gz` natively. **The Google datacenter set is the one class never screened, and it is where SPEC-tuned replacement policies are published to invert.**

**Descriptor coverage** (`python -m loop.offline coverage`): footprint and access rate of all three set-1 traces interpolate the SPEC range; pr.urand's stride 1.000 extrapolates above (the safe direction for a prefetcher claim), bfs.urand's local reuse 0.703 extrapolates below, bfs.kron's write fraction 0.008 extrapolates below. Named in the paper with their direction.

## Evidence (condensed; the pilot reports were deleted, their numbers are here)

- **Pilots on GAP set 1, chip C, start = chip B's best, 16 designs, old space.** First cell (`v1`, 2 seeds, untouched-chip start, playbook read by a GP): `bo_pooled` collapsed on the unseen class (P1 held); rules tied cold BO; the plain agent won (6 designs to 90%, best forecaster, Brier 0.18). Rule signs and firing transferred, magnitudes did not (rules Brier 0.278, 35% wins). Pilots `v4`/`v5` (6 seeds): the cards + recipe memory built on SPEC delayed the decisive move (va_ampm_lite) from designs 2-4 to 7-16 in every seed; cards were cited once in 96 picks; card bets never fired; `handoff` and `rules` never reached 90%; the plain agent's median was 14 designs; the top of the objective was a plateau (90/95/99% coincide). Lesson: facts do not cross a class boundary, strategies do; failures are the most transferable memory; a single recipe design is a bet, an opening pair is a test.
- **Fidelity** (26 chip C designs at 50M/50M): short runs rank correctly (Spearman 0.919, 4 of the short top-5 in the long top-5) and read ~14% low in absolute IPC; the big-LLC advantage survives on all three SPEC workloads. Shorter runs fail (4M/8M 0.77, 2M/4M 0.64).
- **Offline surrogate transfer** (train on A+B, predict C, 810 / 1,834 rows; `python -m loop.offline compare | fair | learned`): every achievable surrogate lands in the same 95.8-96.2% top-5 band (knob GP with chip one-hot 96.2%; physics features 95.9%; CPI stack with curve-predicted misses 95.8%); the CPI stack with MEASURED miss counts reaches 100% from zero observations on C, so the miss-count layer is the whole gap. Miss counts are chip-invariant (B -> C moves MPKI 1.8-4.2%, IPC 25.8%). Prefetchers hide misses rather than remove them (lbm: spp_dev cuts LLC misses 17%, raises IPC 34%). Held-out program: no surrogate transfers from 3 programs (consistent with the literature: 7-29 programs needed). Miss-count GP target: wins only in the first 4-8 designs across chips, not adopted. Where variance lives (Tier A factorial): capacity owns omnetpp (0.76) and half of mcf; the L2 prefetcher owns lbm (0.96); the split flips per workload.
- **Literature** (Sep 8 scan): closest prior work AgentDSE (MLArchSys @ ISCA 2026, arXiv 2606.21836: coding agent tunes a ChampSim hierarchy, ~50 sims vs 1,000 for BO, hypotheses as free text, no transfer, no scoring; its anonymisation ablation showed the LLM is a capable black-box optimiser by itself); LUMINA, MicroEvo, ArchEval; learned cross-program transfer (MetaDSE, OneDSE, PerfVec, Concorde) needs 7-29 programs; RL loses to BO/GA at 10x our budget (ArchGym, OneDSE); mechanistic miss-cost models (interval model TOCS 2009, Van den Steen ISPASS 2015, Aneto MICRO 2026). Nobody has simulator-settled, Brier-scored, pre-registered architectural claims; framing citations POPPER (ICML 2025), FOREAGENT (ACL 2026), Murphy 1973. Verdicts: no RL, no deep learning, no learned workload embedding, no LLM-as-surrogate, no multi-fidelity search.

## Paper

**Claims we can make that ArchAgent cannot:** (i) knowledge carried from earlier searches to a new workload class at all; (ii) forecasts pre-registered and settled by the simulator with a calibration score; (iii) a direct test of extrapolation to an unseen workload class, the problem they name as open; (iv) the memory's behaviour on the class boundary is itself a result (it retrieves procedure, not facts). We do not compete on IPC.

**Report:** best-so-far vs designs with bootstrap CIs over seeds; censored medians to 90/95/99% of each cell's uniform reference; hit fraction; final regret; Brier and reliability diagrams per forecaster (agents, facts, rules, surrogate); the descriptor-range table; the memory as an artifact (cases, facts, strategies with records) and the round prompts; the fidelity table; the admission-gate prediction table; the pre-registration scorecard.

**Limitations, plainly:** chips differ in provisioning, not hierarchy shape; one chip in the headline cells; GAP set 1 only until w2 is defined; placeholder SoC profiles, never team-reviewed; one seed while iterating; strategies come from an LLM's reflection and are only as good as its reading of the trajectory; footprint theory predicts a dedicated cache's miss ratio.

## How to run

`python -m loop.memory check` (offline acceptance checks); `python -m loop.run_chia local smoke <tag> <playbook> <arms>` (the gate before any launch); `python -m loop.run learn <cell> <tag>` (playbook, pool, memory from the cell's tables); `python -m loop.run_chia local <cell> <tag> <playbook> [arms]` with env `SEEDS`, `FIRST_SEED`, `ROUNDS`, `MEMORY_PATH`, `ANALYST_MODEL`; on the VM `SEEDS=1 setsid nohup bash cluster/launch_cell.sh w1 <tag> <arms> &`; `python -m loop.memory consolidate <memory> <out> <cell>` before the next cell; `python -m loop.summarize <report.json> --uniform 300`; **`python -m loop.summarize progress <run.log> [--start <ipc>]` for a cell that is STILL RUNNING** (best-so-far per arm and seed, read from the log's per-design lines; the report itself is only written when a whole arm-seed run finishes, which is far too coarse to watch); `python -m loop.collect uniform 300 <traces>` for a cell's reference; `python -m loop.collect merge <dir>` after fetching the VM's tables.

**The exact w2 launch, for reuse** (`PLAYBOOK` lets a cell reuse another's playbook instead of duplicating files; w2's memory is the consolidated one, not the tag's default):
```bash
python -m loop.memory consolidate results/experiment_w1b_memory.json results/experiment_w2a_memory.json w2
SEEDS=2 ROUNDS=20 MEMORY_PATH=results/experiment_w2a_memory.json PLAYBOOK=results/experiment_w1b_playbook.json \
  setsid nohup bash cluster/launch_cell.sh w2 w2a bo,llm_direct,memory > /dev/null 2>&1 < /dev/null & disown
```
**A smoke writes run memories into the cell's memory namespace** (`experiment_<tag>_memory_run-*.json`), which would be consolidated into the next cell as if they were real runs: delete the smoke's artifacts before launching (`rm -f results/*<smoketag>* results/experiment_<tag>_memory_run-*s<smokeseed>.json`).

**Operational lessons.** Launch long runs detached on the VM (`setsid nohup ... < /dev/null & disown`); kill by process group, never `pkill -f` a broad pattern; never `scp` files into the repo root (a stray `loop.py` shadows the package); the LLM must never be asked to copy long lists (it overflows its output: return ids, rebuild in code); the plain agent must record its run like the others (its trajectories feed the next cell); a round costs one simulation wave (~5 min) plus one Pro call while its simulations fit in 32 cores, so fewer workloads save nothing at one seed; random-arm seeds 0-2 on the smoke suite are cached, so a smoke that must simulate needs seed >= 3; the VM's LLM usage log is wiped by each code push (the Mac's is the lifetime total); measured throughput ~380 simulations/hour on c2d-standard-32 for SPEC, but see below.

**Why w2 is 4x slower than w1, and how to estimate a cell before launching it (Sep 11; two wrong estimates were given before this was measured).** w1b ran 1440 simulations in 4.8 h = 300/hour. w2 runs at 72/hour. The factor of 4.2 is exactly two causes multiplied:
- **The start design, 2.5x.** ChampSim simulates a fixed 10M INSTRUCTIONS but wall time tracks CYCLES, and cycles = instructions / IPC. w1 started from a tuned design at suite IPC 0.601 (75 M cycles per design); w2 starts from the untouched chip at 0.166 (188 M cycles per design). **A stock-chip start costs ~2.5x the compute of a tuned start**, and it only comes back by 24% as the arms improve (the best known design still needs 143 M cycles). This is the price of the headroom the untouched start buys; budget for it.
- **The number of parallel runs, 1.7x.** Rounds are synchronous: a run buys `per_round` designs, blocks until all of them return, then calls the LLM. While it waits on its slowest simulation its cores idle. w1 had 5 arms x 2 seeds = 10 runs filling the 32 cores; w2 has 3 x 2 = 6 and sits at 12-13 of 32 busy. **Cutting arms cuts the work but also cuts the parallelism that hides stragglers.** Raising `SIM_THREADS` does not help (a run only has `per_round` x workloads simulations to issue per round); more concurrent RUNS is the only lever, so an extra seed is close to free in wall clock and buys 50% more data - worth remembering, since seed variance was w1's central weakness.
- **To estimate a cell before launching:** simulations = arms x seeds x rounds x per_round x workloads; rate ~= (parallel runs x cores-per-run utilisation) / cycles-per-design. Sanity-check by computing 10M/IPC per workload at the start design from the cached tables, as `loop.offline headroom` already prints the start.
